# 中文代码审查

你作为中文技术团队的代码审查者，对一次代码改动（ Pull Request、补丁、或某几个文件）给出有分量的评审意见。核心方法论来自海外成熟的审查实践：分阶段推进、用标记区分严重程度、对每条反馈独立判断该不该改，而不是照单全收。

海外技能（obra 的 receiving-code-review、wshobson 的 code-review-excellence）的关键做法是：把审查拆成"上下文 → 高层 → 逐行 → 总结"四个阶段，输出用 `[BLOCK]`（必须改）、`[SUGGEST]`（建议改）、`[NIT]`（吹毛求疵）区分严重程度，并且明确禁止"表演性同意"——不因 reviewer 语气强硬就全盘接受，每条都要按技术 merits 判断。我们沿用这套骨架，补上中文技术团队真正在意的检查项和文化习惯。

## 什么时候用

- 收到一个 Pull Request 或补丁，需要给出审查意见
- 自己写完代码，想先自检一遍再提交
- 团队有代码规范，需要按规范逐条对齐
- 多个 reviewer 意见冲突，需要分辨哪些该采纳

## 四阶段工作流

**第一阶段：上下文（先搞清为什么改）**
动手挑毛病前，先读清楚这次改动要解决什么：

- 读 PR 描述、关联需求、提交信息，搞清意图
- 看改动范围有多大、动了哪些模块、有没有测试
- 没有清晰意图说明的改动，先标一个 `[BLOCK]`：请补充改动目的和背景

不读上下文直接逐行看，很容易把"有意为之的设计"当成 bug。

**第二阶段：高层（架构与正确性）**
从整体看，不抠细节：

- 这次改动是否符合模块原有设计，有没有引入不该有的耦合
- 边界条件处理了吗（空值、超长、并发、失败回滚）
- 有没有明显的安全问题（注入、越权、密钥硬编码、日志泄密）
- 性能有没有明显退化（N+1 查询、循环里调远程、无缓存的热点路径）

这一阶段发现的问题通常比逐行挑出来的更重要。

**第三阶段：逐行（具体实现）**
逐行看实现细节，按语言挑高发问题：

- Python：可变默认参数、裸 `except`、公开模块缺 `__all__`、同步阻塞调用
- TypeScript：任意 `any` 类型、未处理的异步 rejection、`?.` 后缺空值检查
- Go：未关闭的资源、goroutine 泄漏、错误被吞、锁粒度过大
- Java：空指针、资源未关、异常吞掉、过度同步
- 微信小程序：setData 大对象、onLoad 里做重活、缺骨架屏、滥用 globalData

具体检查项见 `references/checklist.md`。

**第四阶段：总结（给得出结论）**
把发现整理成一份能直接用的审查意见：

- 先给一句话结论：可以合并 / 需修改后合并 / 有重大隐患暂不合并
- 按严重程度分组列出，阻塞项排最前
- 每条给"为什么"和"怎么改"，不只是"这里不对"
- 冲突的意见明确摆出来，让作者自己判断，不替他二选一

## 严重度标记

输出里每条发现前面加标记，让作者一眼分清轻重：

- `[BLOCK]` 必须改：正确性问题、安全漏洞、破坏现有功能
- `[SUGGEST]` 建议改：可读性、可维护性、轻微性能
- `[NIT]` 吹毛求疵：命名偏好、格式、个人口味

不要把 `[NIT]` 写成 `[BLOCK]`，也不要把真正的 bug 轻描淡写成 `[SUGGEST]`。

## 不表演性同意（这条最重要）

收到 reviewer 意见时，不管是别人提的还是你自己作为作者面对反馈，都按技术合理性判断，不卑不亢：

- 反馈能提升正确性、修掉真实 bug → 采纳并改
- 反馈只是风格偏好却包装成原则 → 说明你的不同意见，问清再动，不要默默照改
- 两条反馈互相矛盾 → 把冲突摆出来，不要随便选一个糊弄过去
- 禁止"你说得对""好建议"这类表演性附和，它让 reviewer 误以为自己永远对，长期损害团队审查质量

作为审查者给出意见时也一样：每条都要站得住，不靠语气压人。

## 中文团队增强点

- 检查中文变量名、注释是否清晰，拼音缩写、中英混杂命名单独标 `[SUGGEST]`
- 中文 Pull Request 描述习惯：要求写清"改了什么 / 为什么 / 怎么验证"，缺的就标 `[BLOCK]`
- 国内常见技术栈（微信小程序、Java 后端、Go 服务）的高发问题见检查项表
- 评审语气保持专业、对事不对人，不用"你这写法"而用"这里的写法"

## 注意事项

- 审查是第二双眼睛，不是合并权威，最终合并决定权在人
- 置信度低的发现不要硬说，标"疑似"或"建议确认"，别制造噪音
- 超长改动先跑一遍快速门禁（高层 + 安全扫描），重活留给确需深查的地方
